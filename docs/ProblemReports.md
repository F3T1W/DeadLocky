# Technical logs and problem reports

Open **DeadLocky → Report a problem…**. Describe the problem, optionally enter a reply address, then export a ZIP or send it when delivery is configured. The app does not send reports automatically. A failed attempt keeps the fields and report ID; editing either field creates a new ID. There is no automatic retry.

## Local logging and privacy

Logs: `~/Library/Logs/DeadLocky/log-<session>-<sequence>.jsonl`. The sink implements the standard `Microsoft.Extensions.Logging.ILogger` contracts. A single asynchronous reader owns writes, rotation and snapshots. Producers use a bounded 512-entry channel and drop excess entries instead of blocking the UI; a later entry reports the dropped count. An exception tree has a global node/text budget. Disk failure disables writes for the session and does not stop the app.

Keep at most six files, each normally at most 2 MiB, and remove files older than seven days when starting/rotating. Session `.active` markers distinguish normal shutdown from an unfinished session. An unfinished session is **not proof of a crash**. Other live sessions' markers are not removed. System crash reports, Wine/Steam output, app-update helper output, and arbitrary system logs are not collected.

Events contain UTC time, severity, session/operation UUIDs, stage, duration and result. Real operations include installation checks, configuration/cache reads, catalog/network/downloads, archive extraction, VPK validation, profile changes, mod application/conflicts/backup/recovery, game/Steam lifecycle and app updates. Exceptions include their type, bounded message, stack and inner exceptions. Arguments, profile names, queries, HTTP payloads, credentials and the report form are not deliberately logged. URL paths/queries/userinfo, recognized secret assignments/headers, home paths, account names and email addresses are redacted. Redaction is a best-effort additional defense: inspect an exported ZIP before sharing sensitive descriptions.

## ZIP contents and limits

Only `report.json` and up to five allowlisted `Logs/log-*.jsonl` files are included. No scanning of mods, configuration, saves, game folders or personal documents occurs. `report.json` intentionally includes the entered description/email, app version/build, OS/.NET version, process architecture and session ID. Game build is omitted unless reliably known. No hardware serial numbers are collected.

A command in the single log-writer queue flushes and captures a snapshot while writes are paused. It never reads mod deployment state or interferes with its transaction. A file contributes at most its last 1 MiB; the manifest records truncation and redaction expansion is bounded to 2 MiB/file, 6 MiB total. Only regular paths are accepted; symbolic links are rejected, including at the final native file-open step. The ZIP is limited to **8 MiB**, the JSON POST to **12 MiB**, receipts to **8 KiB** and the HTTP operation to **45 seconds**. Description: 1–8,000 characters / 32,000 UTF-8 bytes; reply address: optional, at most 254 characters.

Temporary ZIPs are created in `~/Library/Caches/DeadLocky/Reports/report-<random>/`. Completion, failure and cancellation remove that operation's files. Abandoned report directories older than 24 hours are cleaned on the next export/send. User-saved exports remain at the chosen destination until the user deletes them. Export writes to a temporary sibling before replacing an existing destination confirmed through the native save panel. Closing the report cancels its work; quitting waits for cancellation/cleanup and log shutdown. Auto-update installation waits while the report window is open or busy.

## Activate the Google Apps Script relay (owner only)

The production relay is deployed and its public `/exec` URL is configured in `src/DeadLocky/Info.plist`. It executes as the owner, allows anonymous requests, and has intake enabled with `DAILY_LIMIT=20`. The repository contains no Google credentials. Clearing the endpoint disables Send report while keeping Export ZIP available.

Verified on **2026-10-22** using the GET-only probe: anonymous HTTPS access, the expected `script.googleusercontent.com/macros/echo` ContentService redirect, and JSON health with `enabled=false` before activation and `enabled=true` after activation. Mail-sending authorization was granted by the owner.

Verified live on **2026-10-23**: one report was submitted through the NativeAOT macOS Arm64 app. The matching JSON receipt was accepted by the client, and the matching message arrived in the recipient's iCloud **Inbox**. Received headers contained the expected `To` and `Reply-To` addresses; SPF, DKIM and DMARC passed. The downloaded 24,886-byte ZIP passed its CRC check and contained only `report.json` plus five JSONL logs (437 parseable entries). The manifest's report ID, description, reply address and app metadata matched the submitted draft. No resend or additional test message was triggered. Future test sends still require an explicit command.

To recreate or maintain the deployment:

1. In the recipient owner's Google account, create a project at [Apps Script](https://script.google.com/). Copy `scripts/ReportRelay/Code.js` into the editor. In Project Settings, show `appsscript.json` and replace it with `scripts/ReportRelay/appsscript.json`.
2. Read the code and fixed recipient `f3t1w@icloud.com`. Run `enableReports` once in the editor and grant the owner the mail-sending permission. This enables the service but does not send a message. Alternatively, keep `REPORTS_ENABLED=false` in Script properties while preparing the deployment, then set it to `true` after authorizing and verifying it. No Google credentials belong in the Mac app. The manifest requests only `script.send_mail`, which allows sending mail; it does not grant mailbox-reading access. Default uncaught-exception logging is retained; request data must never be included in thrown errors.
3. Under Project Settings → Script properties, optionally set `DAILY_LIMIT` (default 20, hard cap 50). Set `REPORTS_ENABLED=false`, or run `disableReports`, to reject new reports immediately. Deleting the deployment also disables it. There is no HTTP administration route.
4. Deploy → New deployment → Web app. **Execute as: Me (owner)**; **Who has access: Anyone**, allowing anonymous users. Copy the production `/exec` URL. Do not use `/dev`, “Anyone with Google account”, or a deployment that runs as the accessing user. Workspace policy may prevent anonymous web apps; that account then cannot provide this relay as designed. End users must not need a Google login.
5. Run `python3 scripts/probe-report-endpoint.py 'https://script.google.com/macros/s/YOUR_DEPLOYMENT_ID/exec'`. This performs **GET health only**, follows only the expected HTTPS ContentService redirect and never calls MailApp. Check JSON and anonymous access. It prints no one-time redirect key. Google documents a one-time `script.googleusercontent.com` ContentService URL; actual deployment behavior must be confirmed here. Unexpected/login redirects fail closed.
6. Put the verified URL in the existing `DeadLockyReportEndpoint` string in `src/DeadLocky/Info.plist`, then build the application. This value is public configuration, **not authentication**. An invalid URL disables sending and records a safe configuration error. For a fork without its own deployment, clear this value until the replacement endpoint is verified.
7. **Only after a separate explicit command to send a test report:** submit one report, verify matching JSON receipt ID, anonymous access, the message in iCloud, ZIP contents and replyTo. A receipt means MailApp returned successfully, **not guaranteed Inbox delivery**. Do not claim delivery from a mocked response or health probe.
8. For script updates, deploy a new version of the existing deployment to retain its URL. Re-run the GET probe after changes.

### Admission, quotas and deduplication

Official Google documentation checked **2026-10-22**: consumer accounts allow 100 email recipients/day; Workspace accounts 1,500. Quotas apply per user, reset 24 hours after the first request and can change. `MailApp.getRemainingDailyQuota()` is checked before each new send. Apps Script has a six-minute execution limit and 25 MB total email attachments; the relay's 8 MiB ZIP limit is deliberately lower. Base64 increases HTTP size by roughly one third. Google does not document inbound `doPost` size as the `URLFetch POST` quota: that number applies to outbound URLFetch and is not used as an inbound guarantee.

The relay defaults to 20 new attempts per rolling 24 hours and five per ten minutes, always below a configured cap of 50. Other scripts can consume the owner's mail quota. A script lock serializes admission and the MailApp call; contending requests receive a busy error. The server validates schema, UUIDs, lengths, plain reply addresses, canonical base64, ZIP magic and decoded size. It never unpacks the ZIP. The recipient and subject prefix are fixed; user email is used only for replyTo. It rejects extra fields such as recipient overrides and CRLF in header fields.

Only report ID, state and timestamp enter script properties, plus aggregate admission counters. At most 200 report records remain for seven days; cleanup occurs during requests. Each record is small (below the 9 KB/property limit; total below the 500 KB property-store limit). No description, email or archive is persisted or logged there. Accepted reports themselves remain in the owner's mail according to that account's retention settings.

Before calling MailApp, the service persists `pending` and consumes its attempt budget. Success stores `sent`; retries of a sent ID return the same receipt without sending again. If sending or recording success fails, `pending`/`uncertain` stops automatic resends, even if the client lost the response. The owner must search iCloud by the ID and investigate before manually resolving anything. Do not delete an uncertain record and retry blindly: that can duplicate a message. Deduplication is bounded to seven days; retries after expiry can produce duplicates.

A public endpoint can be abused. Fixed recipient, global/burst caps, quotas, lock and deduplication limit damage but do not authenticate users or prevent someone exhausting the budget. A secret shipped in a public app would not solve this. Disable intake promptly if abused. Robust per-user/IP controls or durable external queues require a different service.

### Errors and verification

If the report window says **Sending is not configured in this build**, its loaded app bundle has no usable `DeadLockyReportEndpoint`. Check the built `.app/Contents/Info.plist`, rebuild and restart the app. The macOS project explicitly tracks the source `Info.plist` as a manifest input because the installed SDK's incremental manifest cache otherwise misses changes to its contents. An older copy in `/Applications` remains unchanged until it is replaced with a new build.

HTML/login, non-2xx responses, unexpected redirect hosts/methods, malformed/oversized JSON, `ok=false`, wrong IDs, offline, timeout and cancellation are not success. The client follows only 302/303 to the expected `script.googleusercontent.com/macros/echo` receipt URL using GET, with no POST body, cookies or credentials forwarded. It does not follow 307/308 with the archive. Retry the unchanged draft to retain the ID; export for manual sharing when delivery is unavailable. Never paste an entire failed HTTP body into logs.

Run local tests with `./.dotnet/dotnet test DeadLocky.slnx` and `node --test scripts/ReportRelay/Code.test.cjs`. They use local files, mocked HTTP and stubbed Google Services; no emails are sent. Native AppKit checks and real deployed mail delivery are separate validation layers.
